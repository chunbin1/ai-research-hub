# 站点默认模型切换(管理员)

## 背景

站点默认模型(所有走公共额度的提问用的那个)目前只存在于环境变量里 ——
`serverLLMConfig()`(`packages/server/src/llm.ts`)从 `ZHIPU_MODEL` /
`ANTHROPIC_MODEL` 拼出配置。要换模型必须编辑 `.env` 并重启服务。

站长的付费套餐用完后需要立刻切到免费模型(如 `glm-4.7-flash`),改文件 + 重启
这条路在生产的 docker 环境里尤其别扭。

已有的 `/settings` 页只管**用户自带模型(BYOK)**,改的是每个用户自己那份配置,
不影响站点默认。这两层是独立的,本设计只动站点默认那一层。

## 目标

管理员在界面上改站点默认**模型名**,保存后下一次提问即生效,不重启。

## 非目标

- 不在界面上改 provider、baseURL 或站长 API key。站长 key 继续只存在于 `.env`,
  永远不进数据库,因此本功能不依赖 `LLM_KEY_SECRET`。
- 不做降级链编辑界面。`.env` 里已有的逗号分隔多模型降级(`withModelFallback`)
  继续工作,但界面只填单个模型名。
- 不动 embedding 模型。文档索引和查询必须在同一向量空间,这点不可配置
  (与 README 中 BYOK 一节的既有约定一致)。
- 不动评测模块。`evalRunner` / `evalGenerator` / `evalJudge` 各自持有模型常量、
  不走 `serverLLMConfig()`,不受本功能影响。

## 方案选择

**采用:存 SQLite,`serverLLMConfig()` 优先读库、回落 env。**

改完下一次请求立即生效,不重启、不写文件;生产的 docker 环境同样适用;数据与
users / traces 同库。代价是 `serverLLMConfig()` 从纯读 env 变成要读库,用
「store 未初始化时直接回落 env」兜住(见下)。

已否决的两个方案:

- **界面写回 `.env` 文件 + 热加载** —— 唯一事实来源仍是 `.env`,运维直觉一致,
  但容器内改 `.env` 会在镜像重建时丢失,另有文件权限、并发写、格式解析等问题。
- **只存进程内变量** —— 重启即退回套餐已用尽的模型,没有解决问题。

## 数据层

新增 `packages/server/src/services/siteSettingsStore.ts`,一张通用键值表:

```sql
CREATE TABLE IF NOT EXISTS site_settings (
  key        TEXT PRIMARY KEY,
  value      TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

导出 `initSiteSettingsTable(db)` / `getSetting(key)` / `setSetting(key, value)` /
`deleteSetting(key)`。本设计只使用一个 key:`default_model`。

**`getSetting` 在 store 未初始化时返回 `null`,不抛错。** 这与
`llmConfigStore` 的「未初始化就抛」不同,是刻意的:`serverLLMConfig()` 会在
不建库的单元测试(`llm.test.ts`)里被直接调用,抛错会让这些测试全部失败。返回
`null` 则天然回落到环境变量,现有测试无需改动。

## 生效路径

`serverLLMConfig()` 中决定模型的那一步改为:

```
getSetting('default_model') ?? process.env.<PROVIDER>_MODEL ?? <内置默认>
```

两个必须保留的细节:

1. **逗号分隔解析保留。** 界面只填单个模型名,但 `.env` 里可能已配
   `glm-4.7,glm-4-flash` 这样的降级链,本次改动不能让它失效。
2. **anthropic 分支同样吃这个 override。** 界面不改 provider,因此
   `default_model` 的语义是「当前 provider 的模型名」,对两个分支一视同仁。

## 接口

新增 `packages/server/src/routes/siteSettings.ts`,注册在 `/api` 前缀下,
全部路由使用 `requireAdmin`(`routes/auth.ts` 已有)。

### `GET /api/site-model`

返回:

```ts
{
  providerId: string | null   // 当前 provider(zhipu | anthropic)
  model: string | null        // 下一次提问生效的模型配置,原始字符串
  source: 'db' | 'env'        // 值来自界面覆盖还是 .env
  envModel: string | null     // .env 里的原值,供「恢复默认」时预览
  suggestedModels: string[]   // 当前 provider 的建议模型名
  configError: string | null  // 站长未配任何 key 时的提示
}
```

`source` 让管理员一眼看出当前是否已被界面覆盖。

`model` 返回的是**生效值的原始字符串**,不做拆分:`.env` 里配了降级链时它会
形如 `glm-4.7,glm-4-flash`,界面原样显示。管理员保存后覆盖值是单个模型名,
降级链随之失效 —— 这是「只改模型名」这一范围下的预期行为,界面上以一行说明
文字点出。

`serverLLMConfig()` 在站长未配任何 key 时会抛错;此处捕获并转为 `configError`
返回,页面照常渲染 —— 管理员正是来这个页面处理问题的。这与 `/llm-config` 的
`configError` 处理方式一致。`configError` 非空时,`providerId` / `model` /
`envModel` 均为 `null`,`suggestedModels` 为空数组,`source` 固定为 `'env'`。

### `PUT /api/site-model`

请求体 `{ model: string }`。流程:

1. `model` 必须是字符串,trim 后非空,否则 400。
2. 用**站长 key + 请求体里的新模型名**构造一份 `LLMConfig`,调用
   `probeLLMConfig()`(`llm.ts` 已有,发一条 `max_tokens=1` 的请求)。
3. probe 失败 → 400,`message` 用 `describeLLMError()` 的原话,**不写库**。
4. probe 成功 → `setSetting('default_model', model)`,返回 `{ ok: true }`。

保存前强制校验,是因为模型名填错(如笔误)会让**全站**公共额度的提问直接失败,
而管理员要到下一次有人提问时才发现。probe 用的是站长自己的 key,所以「套餐用完」
这一事实会如实反映:付费模型 probe 返回 429 失败,免费模型成功。

不提供独立的「测试连接」接口 —— 保存即校验,避免出现「测过但没保存」的中间状态。

### `DELETE /api/site-model`

删除 `default_model`,回落到 `.env`。返回 `{ ok: true }`。

## 前端

### 页面

新增 `packages/client/src/pages/AdminPage.tsx`,路由 `/admin`;数据获取抽到
`packages/client/src/hooks/useSiteModel.ts`,与现有 `useLLMConfig` 同构。
表单沿用 `/settings` 的 antd 写法(`Form` + `Input` + `Alert` + `Button`)。

页面内容:

- 当前生效模型,标注来源(`已在此覆盖` / `来自 .env`)。
- 模型名输入框,带 `datalist` 建议(`glm-4.7-flash`、`glm-4.7`、`glm-4.6`),
  但允许自由填写任意模型名 —— 沿用 `providerPresets.ts` 顶部既定的立场:
  模型迭代快于发版,任何白名单都会先于代码过期。
- 「保存」按钮。保存过程中显示「正在验证…」:这一步会真实调用一次上游,
  有一到两秒延迟,不给反馈会像卡住。
- 「恢复为 .env 默认」按钮,仅在 `source === 'db'` 时出现,点击走 `DELETE`。
- 站长未配 key 时(`configError`)顶部显示 `Alert`。

非管理员访问 `/admin` 时显示「需要管理员权限」。后端已有 403 兜底,前端这一层
只是避免白跑一次请求。

### 入口

`HomePage.tsx` 管理员按钮区(trace / 评估 / 上传 一列)新增一个入口按钮,
仅 `isAdmin` 可见。

### 顺带修正

`providerPresets.ts` 中 zhipu 的 `suggestedModels` 仍是
`['glm-4.7', 'glm-4-flash']`,加入 `glm-4.7-flash`。个人 BYOK 页共用这份建议,
一并受益。

## 影响面

- 只影响 `resolveLLMConfig()` 回落到 `serverLLMConfig()` 的请求
  (即 `config.source === 'server'`)。已启用 BYOK 的用户不受影响。
- 评测模块不受影响(见「非目标」)。
- `GET /api/chat/health` 报告的 `provider` 不变(本功能不改 provider)。
