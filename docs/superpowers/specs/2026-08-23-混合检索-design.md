# 混合检索(BM25 + RRF)

## 背景

单篇 RAG 目前是纯向量 top-k。问「毛利率是多少」时,含答案的那张表在
SpaceX 和腾讯两篇报告里**都排第 6**,前面挤着 5 块讲"净利率""EBITDA 利润率"
的散文 —— 它们和一个短查询的 cosine 距离更近。

现状的应对是把 `RAG_MAX_K` 从 5 调到 10(`.env.example` 的注释自己承认了:
"关键节常排到 6~9 位"),用更大的窗口兜住排序不准。代价是噪音:实测
`citationCoverage` 平均 **0.155**,即塞进 prompt 的上下文约 85% 模型没碰。

### 已实测的事实(全部有数据支撑)

**① 距离阈值跨查询不可比。** 全部 60 块对四种问法的 cosine 距离分布:

| query | 最近 | 中位 | 最远 | ≤0.7 的块数 |
|---|---|---|---|---|
| 毛利率 | 0.5065 | 0.7385 | 0.8319 | 9 / 60 |
| 毛利率是多少 | 0.4787 | 0.7384 | 0.8276 | 10 / 60 |
| 各环节的毛利率区间是多少 | 0.4716 | 0.6764 | 0.7640 | 47 / 60 |
| 火箭发射的毛利率 | 0.4899 | 0.6056 | 0.7006 | **59 / 60** |

查询越长越贴近文档主题,整个分布越向查询平移(中位数 0.7385 → 0.6056),
固定的 0.7 这条线只是被分布滑过去而已。**同一个块换个问法,距离浮动 0.18**
(0.6712 / 0.6503 / 0.5734 / 0.4899),内容一个字没变。

结论:阈值筛的是"提问方式有多贴近文档主题",不是"这块有多相关"。它要求
距离跨查询可比,而这个前提不存在。相对排序则是稳的 —— 所以融合必须用**名次**。

**② 候选池在单篇场景下是空转。** `candidatePool(10) = 40`,而腾讯篇 47 块、
碳酸锂篇 39 块。粗筛几乎等于把整篇取回。真正的选择全发生在应用层的
阈值和截断上,而阈值又近乎全放行 —— 最后起作用的只有 `slice(0, 10)`。

**③ RRF 融合的实测效果(腾讯篇 47 块,目标 chunk 7「2.2 各环节"生意特征"」)**

| query | 向量 | BM25 | RRF(k=60) | RRF(k=10) | BM25 召回数 |
|---|---|---|---|---|---|
| 毛利率是多少 | 6 | 4 | **1** | 2 | 5 |
| 游戏业务的竞争格局 | 4 | 2 | **1** | 1 | 2 |
| 云业务毛利率怎么样 | 3 | 4 | **1** | 1 | 5 |
| 腾讯去年赚了多少钱(负样本) | 11 | — | 11 | 11 | **0** |

三个相关查询,两路单独都进不了第 1,融合后全部第 1。负样本里 BM25 零召回,
RRF 保持向量原名次不变 —— 一路空手时融合等于另一路原样,不会帮倒忙。

## 目标

- 正确块进入 top-3,`citationCoverage` 从 0.155 显著上升
- 精确 token(错误码、财季、代码、具体数字)可被字面命中
- 去掉一段建立在错误前提上的阈值逻辑
- 检索链路对 embedding API 故障不再是单点失效(BM25 路不调任何 API)

## 非目标

- **重排(rerank)**。等评测集就位、能证明收益再说。
- **拒答判据**。唯一跨查询稳定的信号是首名距离(实测四个查询稳定在
  0.47~0.51),但定多少需要评测集校准,不塞进本次。
- **全库问答**。本次仍是单篇(`doc_id` 硬过滤)。
- **查询改写 / 多轮上下文**。已知缺陷,独立处理。

## 方案选择

### 为什么是 BM25 而不是别的第二路

依赖现成:better-sqlite3 编译带 FTS5,`bm25()` 是内置函数(实测
`sqlite 3.53.0` / `FTS5: yes` / `trigram: yes`)。不引入新服务、新依赖、新 key。

附带收益:BM25 不调任何 API。线上曾因 embedding 配额耗尽导致检索静默
返回空(`searchChunks` catch 后 `return []`),整站每个回答都是零依据生成的,
持续多日无人察觉。有了 BM25 这条腿,同样的故障下检索会降级而不是归零。

### 中文分词:trigram + 查询 n-gram 展开

`icu` 分词器本机不可用(实测 `no such tokenizer: icu`),中文又没有空格。
选 `tokenize='trigram'`,查询侧把原句切成所有 3-gram 后 OR 起来:

```
"毛利率是多少"  →  MATCH  "毛利率" OR "利率是" OR "率是多" OR "是多少"
```

不需要任何分词库。IDF 自动挑出稀有的那个:`毛利率` 全篇只在 5 块出现,
权重压倒 `是多少`。上表的 BM25 名次就是这么跑出来的。

**注意**:数字和标点必须包在双引号里,否则 `42.3` 会触发
`fts5: syntax error near "."`。

### 融合用 RRF 而不是加权分数

向量距离约 0.47~0.83,BM25 分数是负数且无下界(实测 -0.445 / -6.253),
没有共同尺度。更根本的是事实 ①:距离的绝对值跨查询不可比,而名次可比。

```
RRF(d) = Σ 1 / (k + rank_i(d))     k = 60
```

## 架构

```
query
 ├─ 向量路   Chroma（不动）                → 排名列表
 └─ BM25 路  SQLite FTS5 trigram          → 排名列表
                  ↓
            RRF(k=60) 按名次融合、按稳定 ID 去重
                  ↓
            取前 maxK（5）→ prompt
```

## 模块划分

### `services/chunkFts.ts`

FTS5 表的建立、写入、查询、删除。表与主库同文件(一个事务域、一份备份、
`reset:dev` 顺手可扩展)。

```sql
CREATE VIRTUAL TABLE chunk_fts USING fts5(
  doc_id UNINDEXED, chunk_index UNINDEXED, section_title, content,
  tokenize='trigram'
)
```

`doc_id` 走 `UNINDEXED` 列 + 普通 `WHERE`,与 `MATCH` 组合使用 —— 与向量路
一样是**预过滤**,不是查完再删。

### `services/rrf.ts`

纯函数。输入若干个排名列表,输出融合后的列表。按稳定 ID 去重(同一 chunk
在两路都出现时只占一个位置)。

### `services/retrieval.ts`

编排:并发发两路 → RRF → 截断。`chat.ts` 改调它。**任一路抛错时不整体失败**,
降级为另一路并 `markDegraded`。

### `scripts/reindex.ts` —— 硬前置

现有文档的 FTS 表是空的,不回填 BM25 对老文档永远零召回。原文在
`data/raw/*.md`,重建不需要任何 API 调用。

同时它也是将来更换 embedding 模型的前提(换模型 = 维度变化 = 库里所有向量
作废;当前 embedding-3 是 2048 维,bge-m3 是 1024 维)。

支持两种入口:全量重建、指定 doc_id。

### 接线改动

- `routes/documents.ts` 上传时同时写 FTS;删除时同时删 FTS
- `ragConfig.ts` 摘掉 `distanceThreshold` / `minK`,`maxK` 10 → 5
- `chat.ts` 的 `doc_retrieval` span 记两路各自名次与融合后名次

## 可观测

融合会让"为什么这块排在这"变得更难回答,因此 trace 必须记录中间态:

```jsonc
"retrieval": {
  "vectorRanks": [39, 28, 9, 27, 44, 7, ...],
  "bm25Ranks":   [46, 29, 4, 7, 23],
  "fusedTop":    [7, 39, 4, 28, 29],
  "bm25Recalled": 5,
  "degraded": null
}
```

没有这个,调 `k` 值就是盲调。

## 验收

用一组固定问题(覆盖表格数值、定性结论、跨章节、口语提问、报告里没有的)
在改动前后各跑一遍,比较:

- `citationCoverage` —— 基线 0.155,应显著上升
- 正确块名次 —— 目标进 top-3
- 负样本 —— 报告里没有的问题不应因 BM25 而多召回噪音

这组问题同时是评测集的雏形。

## 风险

| 风险 | 应对 |
|---|---|
| trigram 索引约为原文 3 倍体积 | 当前两篇无所谓;全库问答时重新评估 |
| 查询不足 3 字符时无 trigram | BM25 空手,自动退化为纯向量,可接受 |
| BM25 对长块有长度惩罚 | 正是需要融合而非替换的原因(chunk 7 是大表,BM25 只给第 4) |
| 摘掉阈值后永远返回 maxK 块 | 阈值本就近乎全放行(59/60),现状并未提供拒答能力,不构成回退 |
| FTS 与 Chroma 写入不同步 | 上传路径同事务写 FTS;`reindex` 可随时重建对齐 |
