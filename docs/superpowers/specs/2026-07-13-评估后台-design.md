# 研报站 RAG 评估后台 设计文档

> 日期:2026-07-13
> 状态:设计已确认,待写实现计划
> 分支:`feat/eval`(从含 auth 的 master `03daa68` 拉出;评估需 `requireAdmin`)
> 来源:移植/适配 `~/myCode/docmind` 的 eval 系统

## 1. 目标

给管理员一个 **`/eval` 后台页**:列表展示每篇研报的四维 RAG 质量指标,每行可**手动异步触发评估**,顶部一条**总体统计**。用途是质检 + 调参(调完 `RAG_MAX_K`/阈值后重跑,看召回率变化)。读者不可见。

## 2. 四维指标(RAGAS 式自评估)

对每篇报告:LLM 自动**抽样出题**(约 15 道"问题+期望答案+来源段落"),逐题跑**与线上完全相同的检索+答题链路**,再打四维分:

- **召回率 context recall**(规则判定):该题来源段落有没有被检索到(命中 chunk_id,或期望答案文本实质出现在检索到的块里)。
- **精确率 context precision** / **忠实度 faithfulness** / **相关性 answer relevancy**:一次 LLM-as-Judge 调用出三分(0–1)。

一篇的最终指标 = 各题四维分的平均。

## 3. 关键决策

| 点 | 决定 |
|----|------|
| 定位 | 管理员专用后台;所有 eval 路由 `requireAdmin` |
| 出题量 | **抽样**,默认每篇 15 题(`EVAL_SAMPLE_SIZE` 可配),非全量 |
| 答题链路 | **复用线上真实链路**(同 `searchChunks`/`RAG_MAX_K`/同 system prompt),指标才反映真实质量、才能调参对比 |
| 执行方式 | **异步后台跑**;点按钮该行 running→done,前端轮询刷新 |
| 存储 | **精简自研 2 表**(非 docmind 4 表):`eval_runs`(每篇一次汇总)+ `eval_results`(每题明细),按 doc_id 存,取最新 run |
| 限次 | 评估的答题调用是管理员内部触发,**不计**个人/全局限次 |
| Judge 模型 | `ZHIPU_JUDGE_MODEL`(默认 glm-4.7),可与线上答题模型不同 |

## 4. 后端

### 4.1 移植(适配)
- **`services/evalJudge.ts`**(移植):`scoreContextRecall(retrievedChunkIds, groundTruthChunkId, expectedAnswer?, retrievedContents?)` 规则召回;`scoreLLMMetrics(question, retrievedChunks, answer, expected)` 一次调用出 precision/faithfulness/relevancy + token usage。
- **`services/llmThrottle.ts`**(移植):自适应限流 + 429 退避,供 judge/答题的上百次调用共用。
- **`services/evalGenerator.ts`**(移植+改):从**抽样**分块出题(不是每段);抽样源为该 doc 的分块(用 `markdownParser` 重解析 raw markdown 得 chunk 列表 + chunk_index,ground_truth = `${docId}_chunk_${index}`,与 chroma 中 id 对齐)。

### 4.2 自研(精简)
- **`services/evalStore.ts`**:
  - `eval_runs(id, doc_id, status['running'|'done'|'failed'], question_count, avg_recall, avg_precision, avg_faithfulness, avg_relevancy, started_at, finished_at)`
  - `eval_results(id, run_id, question, expected, retrieved_sections(JSON), answer, recall, precision, faithfulness, relevancy, reasoning(JSON), created_at)`
  - 接口:`initEvalTables(db)`、`createRun(docId)`、`finishRun(runId, aggregate)`、`failRun(runId)`、`insertResult(runId, r)`、`getLatestRunByDoc(docId)`、`getResults(runId)`、`listLatestRunsAllDocs()`、`aggregateStats()`(顶部统计)、`markStaleRunsFailed()`(启动崩溃恢复)。
- **`services/evalRunner.ts`**(改):`runEval(docId)` —— 生成抽样测试集 → 逐题:`searchChunks`(同线上)+ 复用线上 system prompt 组装 + `streamChat` 收全答案(非 SSE)+ `scoreContextRecall` + `scoreLLMMetrics` → `insertResult` → 汇总 `finishRun`。**fire-and-forget 异步**,失败 `failRun`。同一 doc 已有 running 则拒绝重复触发。

### 4.3 路由(`routes/eval.ts`,全部 `requireAdmin`)
- `GET /api/eval` → `{ stats: {docsEvaluated, avgRecall, avgPrecision, avgFaithfulness, avgRelevancy}, reports: [{doc_id, filename, status, question_count, avg_recall/precision/faithfulness/relevancy, finished_at}] }`(所有报告 join 各自最新 run)
- `POST /api/eval/run` body `{docId}` → 起异步 run,返回 `{status:'running', runId}`;若已在跑返回 409
- `GET /api/eval/:docId` → 该篇最新 run + 每题明细
- `index.ts`:`initEvalTables(db)` + `markStaleRunsFailed()` + 注册 `evalRoutes`

## 5. 前端

- **`hooks/useEval.ts`**:`fetchDashboard()`、`runEval(docId)`、`fetchDetail(docId)`;dashboard 有 running 时轮询(~3s)。
- **`pages/EvalDashboard.tsx`**:
  - 顶部统计条:已评估篇数 + 全站平均 召回/精确/忠实/相关。
  - 表格:报告名 | 召回 | 精确 | 忠实 | 相关 | 状态(未评估/评估中/已完成/失败)| 「跑评估」按钮 + 「明细」入口。评估中禁用该行按钮 + 转圈。
- **`pages/EvalDetailPage.tsx`**:每题一行/卡片——问题、期望答案、检索到的章节、AI 答案、四维分、judge 理由(诊断召回低的原因)。
- 路由 `/eval`、`/eval/:docId`(管理员限定;非管理员重定向首页)。首页 header 管理员可见入口「📊 评估」(挨着 🔍 trace)。

## 6. 成本与稳健

- 默认 15 题/篇,`EVAL_SAMPLE_SIZE` 可配;`llmThrottle` 扛 429。
- 评估调用不计限次(管理员内部)。
- 服务重启:`markStaleRunsFailed()` 把残留 running 翻 failed,不永久卡"评估中"。
- judge 解析失败该维度记 0 + 保留原文(便于排查)。

## 7. 测试

- `evalJudge.scoreContextRecall` 单测:命中 chunk_id → 1;期望答案文本出现在检索块 → 1;都不满足 → 0;过短答案不误判。
- `evalStore` 单测:createRun/insertResult/finishRun 往返 + `getLatestRunByDoc` 取最新 + `aggregateStats` 聚合。
- 端到端手测:对碳酸锂报告 `POST /api/eval/run` → 轮询 `GET /api/eval` 状态 running→done → `GET /api/eval/:docId` 看四维分 + 明细;浏览器 `/eval` 页触发 + 展示。

## 8. 非目标

- 不做多测试集管理/多 run 对比(每篇只留最新一次)。
- 不做人工标注 ground truth(纯 LLM 自动出题)。
- 不给读者展示评估分。
- 不做定时自动评估(仅手动触发)。
